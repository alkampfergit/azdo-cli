**When ending a work session**, you MUST complete ALL steps below. Work is NOT complete until `git push` succeeds.

**MANDATORY WORKFLOW:**

1. **File issues for remaining work** - Create issues for anything that needs follow-up

3. **Update issue status** - Close finished work, update in-progress items

   git pull --rebase
   bd dolt push

The PATCH body carries **only** the supplied fields that actually differ (Azure DevOps leaves omitted properties alone, and the docs warn that sending anything outside the updatable set throws or is ignored), so `--title` cannot disturb the description, and an all-matching invocation is a no-op with no write at all — the current values come free from the fetch `resolvePullRequestTarget` already does. `--description` replaces **literally**: no template lookup, because `pr open`'s compose-with-template would re-prepend the repository template on every edit. `pr open` gains `--description-file`; `pr update` gains `--title-file` / `--description-file`; a path of `-` means stdin and was implemented inside the shared `resolveCommentBody` reader, so `pr comments add|edit|reply --file -` works too. `pr open --description ''` deliberately still means "use the template" (an empty `--description-file` is an error). Review round: command-level stdin regression tests now cover `pr open --description-file -` and `pr comments add|edit|reply --file -` (they assert the read hits fd 0, not a file named `-`); `README.md` carries the new command and the file/stdin options per Constitution VII; and the two `pr open` / `pr update` actions were split into `resolveOpenDescription`, `resolveRequestedFields` and `diffRequestedFields` to clear SonarCloud's cognitive-complexity rule.
